## Что мы делаем?

Создаём второй контейнер: минимальное совместимое окружение Node.js/npm и стартовый скрипт. DSH устанавливается после запуска контейнера под непривилегированным пользователем. Отдельная папка владельца на хосте целиком монтируется в `/home/dsh`; `HOME=/home/dsh`. В ней сохраняются установка, настройки и пользовательские рабочие данные. Настоящий домашний каталог владельца сервера не монтируется.

Контейнер не публикует свой веб-порт на хост. Постоянный пароль проверяет [шлюз](auth-gateway.md), которому DSH передаёт только текущий стартовый токен через выделенный служебный том. Данные и сертификаты шлюза недоступны DSH. Резервное копирование вне рамок проекта.

Источник установки — [официальный репозиторий](https://github.com/deepseek-ai/deepseek-harness) и опубликованный им npm-пакет. [Документация веб-режима](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/README.md) на 2026-10-31 требует конкретный IP для bind и описывает public URL и trusted host. Эти требования перепроверяются для закреплённого npm-релиза.

Общий прототип авторизации выполняется до основной реализации обоих контейнеров. Итоговые параметры передаются в [план Compose и документации](repository-and-compose.md). Указанные будущие пути являются предлагаемой структурой проекта.

## План

- [ ] Проверить запуск выбранного релиза в контейнере.
  - [ ] Согласовать точную версию npm-пакета с прототипом шлюза.
  - [ ] Проверить требования опубликованного пакета к Node.js, libc, нативным модулям и внешним исполняемым файлам.
  - [ ] Выбрать минимальный совместимый базовый образ с закреплённой версией.
  - [ ] Проверить поддерживаемые Linux-архитектуры и записать фактически проверенную матрицу.
  - [ ] Проверить работу инструментов DSH с ограниченными правами; отдельно выявить требования его собственной песочницы без автоматического включения privileged или unconfined.
  - [ ] Зафиксировать пути состояния, параметры запуска и необходимые зависимости в общем `docs/dsh-integration.md`.

- [ ] Подготовить сохраняемый домашний каталог.
  - [ ] Настроить HOME, рабочую директорию и UID/GID непривилегированного процесса.
  - [ ] Разместить DSH_HOME внутри `/home/dsh` с учётом фактического поведения выбранного релиза.
  - [ ] Разместить установку DSH и npm cache внутри домашнего каталога.
  - [ ] Задать отдельный подкаталог домашних рабочих проектов, не смешивая их с файлами установки.
  - [ ] Реализовать проверку прав bind mount с понятной ошибкой вместо chmod 777 или рекурсивного изменения владельцев существующих данных.
  - [ ] Определить процедуру подготовки пустого каталога на хосте с нужным UID/GID.
  - [ ] Убедиться, что обязательное сохраняемое состояние не остаётся только в записываемом слое контейнера.

- [ ] Реализовать установку при старте.
  - [ ] Добавить стартовый скрипт в образ без предустановленного DSH.
  - [ ] Требовать точную версию DSH, исключив неявное обновление по latest.
  - [ ] Устанавливать DSH непривилегированно в отдельный каталог версии с фиксацией разрешённых зависимостей.
  - [ ] Защитить установку от одновременной записи двумя процессами с одним домашним каталогом.
  - [ ] Переключать активную установку только после успешного завершения и проверки исполняемого файла.
  - [ ] Повторно использовать исправную установленную версию без обращения к npm для её переустановки.
  - [ ] Обрабатывать прерванную установку без удаления пользовательских настроек и проектов.
  - [ ] При недоступности registry на первом запуске завершаться с ограниченными повторами и ясной диагностикой.
  - [ ] Предусмотреть явное обновление сменой версии; не обещать совместимость отката при изменении формата данных upstream.

- [ ] Реализовать безопасный веб-запуск и передачу токена.
  - [ ] Вычислять конкретный адрес интерфейса нужной Docker-сети при каждом старте вместо wildcard bind или жёсткого IP.
  - [ ] Запускать веб-профиль без открытия браузера с явными публичным URL и доверенным hostname.
  - [ ] Получать стартовый токен через проверенный интерфейс выбранной версии; при перехвате stdout использовать строгий разбор ожидаемой строки без записи исходного URL в логи.
  - [ ] Атомарно публиковать токен с поколением процесса в отдельном служебном томе с минимальными файловыми правами.
  - [ ] Сбрасывать готовность и прежнюю запись токена перед новым запуском, чтобы шлюз не использовал её как актуальную.
  - [ ] Не предоставлять шлюзу доступ к файлу credentials или остальному HOME ради обмена токеном.
  - [ ] Отмечать контейнер готовым только после установки, готовности HTTP-сервера и публикации текущего токена.
  - [ ] Передавать сигналы остановки DSH и корректно завершать дочерние процессы.
  - [ ] Ограничить время остановки и обработать аварийный выход DSH без сохранения ложной готовности.

- [ ] Ограничить полномочия контейнера.
  - [ ] Запускать DSH без root, privileged, Docker socket и host namespaces.
  - [ ] Отключить лишние Linux capabilities и включить запрет повышения привилегий.
  - [ ] Использовать стандартный seccomp-профиль, фиксируя необходимые совместимые ограничения по результатам запуска DSH.
  - [ ] Сделать корневую файловую систему read-only, выделив HOME, служебный том и временные tmpfs для необходимых записей.
  - [ ] Определить рабочие лимиты CPU, памяти, PID и временных файлов с учётом первой установки.
  - [ ] Разделить отсутствие опубликованного порта и ограничения исходящего трафика: npm и API моделей требуют выхода в сеть.
  - [ ] Описать защиту сервисов хоста, LAN и metadata endpoints через применимые правила хоста; не объявлять обычную Docker bridge-сеть полной сетевой изоляцией.

- [ ] Проверить жизненный цикл на временных пользовательских данных.
  - [ ] Проверить первый запуск с пустым HOME.
  - [ ] Проверить повторный запуск без переустановки DSH.
  - [ ] Проверить пересоздание контейнера с сохранением настроек, тестовой истории и рабочих файлов.
  - [ ] Проверить вход через шлюз после перезапуска DSH с новым токеном.
  - [ ] Проверить восстановление после прерывания установки и после завершения процесса DSH.
  - [ ] Проверить понятные ошибки при неверных правах HOME, нехватке места и недоступном registry.
  - [ ] Проверить явное обновление на совместимую тестовую версию без очистки HOME.
  - [ ] Проверить реальные UID/GID, mounts, capabilities и ограничения ресурсов контейнера.
  - [ ] Проверить, что токен отсутствует в Docker logs и диагностике с использованием искусственного тестового значения.
