## Что мы делаем?

Создаём первый из двух контейнеров: компактный шлюз с формой входа в стиле DSH, постоянным паролем владельца, reverse proxy и опциональным автоматическим HTTPS. Логин по умолчанию — `token`. После входа адаптер автоматически обменивает текущий токен DSH на его штатную браузерную cookie. Исходники DSH и его проверки авторизации не изменяем. Это одно пользовательское окружение, без регистрации и разграничения доступа между несколькими владельцами.

Предусмотрены два режима: самостоятельный HTTPS с Let's Encrypt и HTTP за внешним reverse proxy, который обслуживает публичный HTTPS. Во втором режиме ACME полностью отключён. Резервное копирование вне рамок проекта.

Официальный upstream найден через [сайт DSH](https://deepseek.com/harness/). На 2026-10-31 в [BrowserAuth](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/connection/src/browser-auth.ts) токен создаётся на запуск, а [Connection](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/connection/README.md) описывает сохраняемый секрет подписи cookie. Протокол необходимо проверить на выбранной опубликованной версии, а не считать ветку `master` стабильным контрактом.

Зависимости: прототип выполняется совместно с начальным этапом [контейнера DSH](dsh-runtime.md); итоговую конфигурацию использует [план репозитория и Compose](repository-and-compose.md). Имена будущих каталогов и настроек ниже являются проектными решениями, а не уже существующими файлами.

## План

- [ ] Проверить адаптер на закреплённой версии DSH.
  - [ ] Выбрать опубликованную версию DSH для общего интеграционного прототипа.
  - [ ] Подтвердить обмен стартового токена на браузерную cookie через корневой маршрут с сохранением публичного Host.
  - [ ] Подтвердить доступ к HTTP API с выданной cookie.
  - [ ] Подтвердить авторизацию WebSocket с выданной cookie.
  - [ ] Проверить сохранение браузерной сессии после перезапуска DSH с прежним домашним каталогом.
  - [ ] Проверить новый вход после перезапуска с обновлённым токеном.
  - [ ] Зафиксировать совместимый протокол в `docs/dsh-integration.md`, включая ответы об ошибках и привязку cookie к адресу.

- [ ] Определить интерфейс двух контейнеров.
  - [ ] Закрепить сервисные имена `gateway` и `dsh` и отдельный маршрут формы входа, не конфликтующий с DSH.
  - [ ] Определить отдельный служебный том для передачи текущего токена и поколения процесса: DSH пишет, шлюз читает; домашний каталог DSH шлюзу не монтируется.
  - [ ] Определить атомарную замену записи токена и поведение шлюза при отсутствующей, повреждённой или устаревшей записи.
  - [ ] Закрепить публичный URL как явную настройку; upstream задаётся доверенной конфигурацией и не выбирается из пользовательского запроса.
  - [ ] Разделить постоянное состояние шлюза, ACME-данные, служебный токен и домашний каталог DSH.
  - [ ] Выбрать реализацию шлюза на поддерживаемых библиотеках HTTP proxy, сессий, хеширования паролей и ACME; описать выбор в `docs/dsh-integration.md`.

    - [ ] Отклонять запуск с отсутствующими обязательными учётными данными вместо включения публичного доступа.
    - [ ] Реализовать вход с ограничением частоты попыток и одинаковым сообщением о неверных учётных данных.
    - [ ] Реализовать собственную сессию шлюза с ограниченным сроком, сменой идентификатора при входе и защищёнными атрибутами cookie.
    - [ ] Реализовать выход с отзывом сессии шлюза и очисткой браузерной cookie DSH.
    - [ ] Определить отзыв активных сессий при смене пароля.
    - [ ] Защитить изменяющие состояние маршруты входа и выхода от межсайтовых запросов.
