# Шлюз rdsh

## Проверенный протокол DSH

Для первого выпуска выбрана опубликованная версия `@deepseek-ai/dsh@0.2.1-rc.5`.
Контейнерный прототип runtime подтвердил:

- `GET /?token=…` с публичным `Host` возвращает `303`, `Location: ./` и cookie `dsh-auth-*`.
- HTTP API отклоняет запрос без cookie; WebSocket `/api/remote.mux` с cookie и корректным `Origin` принимает upgrade.
- После перезапуска DSH стартовый токен меняется, старый токен получает `401`.
- При сохранении домашнего каталога уже выданная браузерная cookie продолжает работать.

Полные условия и воспроизводимый прототип принадлежат [интеграции runtime](dsh-integration.md).
Смена версии DSH требует повторной проверки этого протокола до её включения в поддерживаемый пример.
Это адаптер под конкретный upstream, а не универсальная система SSO.

## Контракт контейнеров

`gateway` обращается к фиксированному `DSH_UPSTREAM` (обычно `http://dsh:3080`).
Адрес upstream никогда не берётся из браузерного запроса или handoff-файла.
`dsh` атомарно заменяет `/run/rdsh/connection.json` с двумя строковыми полями:
`token` и `generation`. Шлюз монтирует этот служебный том только для чтения.
Отсутствующий, повреждённый или меняющийся handoff закрывает доступ с временной ошибкой,
а не отключает проверку авторизации. Возможен максимум один дополнительный обмен при смене поколения.
HOME DSH, его файл credentials и модельные ключи шлюзу не монтируются.

Публичный URL задаётся явно, использует HTTPS и корневой путь. Prefix deployments в первом выпуске не поддерживаются.
Служебные маршруты шлюза занимают `/_rdsh/`: `login`, `logout`, `style.css`, `health`.
Все остальные маршруты принадлежат DSH и требуют сессию шлюза, в том числе статические файлы, API и WebSocket.
Прямой браузерный обмен query-токена DSH запрещён.

Реализация: один Go-процесс, `net/http/httputil.ReverseProxy` для потоков и WebSocket,
`golang.org/x/crypto/bcrypt` для пароля, `github.com/gorilla/securecookie` для подписанных cookie,
`golang.org/x/crypto/acme/autocert` для ACME и продления сертификатов.
Сессии дополнительно хранятся в ограниченной серверной таблице с отзывом и временем жизни.
Собственная криптография и отдельный сервис базы данных не нужны.

| Настройка | Назначение / значение по умолчанию |
| --- | --- |
| `PUBLIC_URL` | Обязательный внешний HTTPS origin, например `https://dsh.example.com` |
| `TLS_MODE` | `external` (HTTP за существующим TLS proxy) или `auto` (ACME) |
| `HTTP_ADDR` | `:8080` |
| `HTTPS_ADDR` | `:8443`, только в `auto` |
| `AUTH_USERNAME` | `token` |
| `AUTH_PASSWORD_HASH` | bcrypt-хеш; основной способ конфигурации |
| `AUTH_PASSWORD_HASH_FILE` | Необязательный путь вместо хеша в env; вместе задавать нельзя |
| `SESSION_SECRET_FILE` | Необязательный путь для совместимости; по умолчанию ключ создаётся в памяти |
| `SESSION_TTL` | `12h`; допустимо `5m`–`720h` |
| `DSH_UPSTREAM` | `http://dsh:3080` |
| `DSH_HANDOFF_FILE` | `/run/rdsh/connection.json` |
| `STATE_DIR` | `/var/lib/rdsh`, постоянный ACME cache в подкаталоге `acme` |
| `TRUSTED_PROXIES` | Список CIDR через запятую; пустой означает не доверять forwarded IP |
| `ACME_EMAIL` | Контакт для ACME, необязательный |
| `ACME_DIRECTORY_URL` | Необязательная альтернативная ACME directory, например staging |

Образ принимает build args `RDSH_UID`/`RDSH_GID`, по умолчанию `1000`/`1000`.
Каталоги состояния и handoff создаются с тем же владельцем, что и в образе DSH,
чтобы начальное заполнение named volume не зависело от порядка создания контейнеров.

## Вход и отзыв доступа

Шлюз принимает обычную HTML-форму со стабильными `username`, `password` и autocomplete-подсказками.
Страница не загружает внешние шрифты, скрипты или аналитику. Небольшой оригинальный знак rdsh
и нейтральная светлая/тёмная тема сочетаются с интерфейсом DSH, не заявляя официального происхождения проекта.

`hash-password` читает пароль из TTY без echo (с повторным вводом) либо из stdin.
Пароль должен занимать 12–72 байта UTF-8; ограничение связано с bcrypt.
Команда печатает только хеш; пользователь записывает его в `.env` в одинарных кавычках.
Она доступна до настройки сервера через `docker compose run --rm --no-deps gateway hash-password`.
`generate-secret` оставлена для совместимости, но отдельный секрет для обычной установки не нужен.
Шлюз не запускается без корректного хеша в env или явно указанном файле. При выборе файлов
они должны быть доступны контейнерному UID/GID, но не другим пользователям (`0600` или `0640`).
По умолчанию ключ подписи создаётся криптографическим генератором в памяти при каждом запуске.

Вход и выход защищены CSRF-токенами, проверкой Origin и Sec-Fetch-Site.
Лимит — пять попыток входа в минуту с одного клиентского IP и тридцать суммарно;
таблица лимитов ограничена. При заполнении лимита возможна временная недоступность входа,
но уже действующие сессии продолжают работать. За внешним прокси следует указать только его реальные доверенные CIDR,
иначе все пользователи за этим прокси разделяют один IP-лимит. Внешний прокси должен перезаписывать или корректно дополнять X-Forwarded-For.

После входа браузер получает подписанную cookie шлюза и cookie DSH с `Secure`, `HttpOnly`, `SameSite=Strict`.
Шлюз хранит свою таблицу сессий в памяти; подпись cookie без записи в таблице не даёт доступа.
Native cookie DSH хранится также внутри соответствующей сессии и подставляется upstream-серверу шлюзом.
Cookie шлюза, внешний Authorization и forwarded-заголовки не пересылаются в DSH.

При смене поколения DSH шлюз получает новую native cookie до отправки пользовательского запроса.
Если DSH неожиданно ответил `401`, запрос не повторяется; следующий запрос выполнит новый обмен.
Это исключает двойную отправку сообщения или другое повторение изменяющего состояние действия.
На время установки или сбоя DSH шлюз возвращает временную ошибку, а не публичный интерфейс.

`/_rdsh/logout` показывает подтверждение выхода. Отзыв или истечение сессии закрывает связанные HTTP-потоки и WebSocket,
в том числе соединения без входящего трафика. Лимит активных сессий — 256.
Перезапуск **DSH** сохраняет вход шлюза, а перезапуск **gateway** завершает все его сессии.
Чтобы сменить пароль и отозвать доступ, обновите хеш в `.env` и пересоздайте gateway:
`restart` не перечитывает окружение. При использовании файла также нужен recreate,
если файл bind mount был атомарно заменён новым inode на хосте.

## HTTPS и существующий reverse proxy

В `external` запускается только HTTP listener. ACME-клиент, cache и TLS listener не создаются.
Внешний прокси обязан обслуживать указанный публичный HTTPS URL, сохранять Host/Origin,
передавать WebSocket upgrade и не буферизовать потоковые ответы.
Secure-cookie определяется по обязательному публичному HTTPS URL, а не недоверенному X-Forwarded-Proto.

В `auto` autocert обслуживает TLS-ALPN-01 и HTTP-01, ограничивает выпуск указанным hostname,
хранит account/cert state в `STATE_DIR/acme` и автоматически обновляет сертификат.
Включение этого режима означает использование ACME с принятием условий выбранного сервера.
HTTP принимает ACME challenge и перенаправляет GET/HEAD на фиксированный HTTPS origin;
формы по HTTP не принимаются. Локальный healthcheck доступен отдельно.

Тесты не требуют действующего публичного домена или платной модели:

```sh
cd gateway
go test -race ./...
go vet ./...
RDSH_ACME_TEST=1 go test -race -run TestACMEIssuanceCacheAndRenewal -v -timeout 90s .
```

Последняя команда требует Docker: она создаёт временный Pebble, собственную тестовую CA и короткоживущие сертификаты.
Проверяются реальная TLS-ALPN domain validation, выпуск, чтение cache без сети и автоматическое продление.
Проверенный стенд — Linux-контейнеры на OrbStack ARM64 с доступом к host gateway.
Это не выдача production-сертификата Let's Encrypt и не проверка DNS/фаервола конкретного сервера пользователя.

## Браузерная проверка

В Safari проверены отображение формы, понятная ошибка неверного пароля, переход в реальный DSH после верного входа,
выход и отказ повторного доступа без входа. На viewport 390×844 все элементы формы помещаются без обрезки;
проверен переход фокуса клавишей Tab. Модельные запросы для проверки не выполнялись.
Во время этой проверки устранено влияние `Referrer-Policy: no-referrer` на `Origin: null` при отправке HTML-формы:
шлюз использует `same-origin`, сохраняя строгий отказ запросам с `Origin: null`.
Внешним сайтам Referer при этом не передаётся.

В нативном Google Chrome 155 на macOS дополнительно проверены вход с верным паролем в полный интерфейс DSH
и выход с возвратом на страницу входа. Проверка выполнена через интерфейс браузера; недоступность CDP у встроенного
Chromium-инструмента ей не помешала.

Пользователь отдельно ограничил проверку самим входом: тестовый пароль в личный Keychain или хранилище Chrome не сохранялся,
проверка сохранения/автозаполнения исключена из объёма. Предложения Safari и Chrome сохранить пароль были отклонены.
Наличие правильных autocomplete-атрибутов и показ предложения сохранить пароль не равнозначны проверенному автозаполнению.

Интеграционные проверки Compose прошли для внешнего TLS-прокси на хосте, внешнего nginx в Docker-сети
и встроенного автоматического TLS с тестовым Pebble. Проверены реальный DSH, WebSocket, повторный вход после его пересоздания,
сохранение HOME, отзыв после пересоздания gateway и отсутствие пароля/токена в логах.
Образ шлюза работает с непривилегированным UID/GID; отдельно проверена связка с пользовательским UID 501 / GID 20.
Handoff открывается без следования символическим ссылкам и без блокировки на FIFO: DSH не может перенаправить это чтение
в закрытые файлы шлюза или подвесить обработчик подменой типа файла.
