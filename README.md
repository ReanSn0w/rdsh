# rdsh

Развёртывание [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)
на своём сервере: два контейнера, сохраняемый домашний каталог и привычный вход
по логину и паролю. Это самостоятельная оболочка, а не официальный продукт DeepSeek.

```text
Браузер ── HTTPS ── [внешний reverse proxy, если нужен] ── gateway ── dsh
                                                          │         │
                                                     вход + TLS  /home/dsh
```

- **gateway** обслуживает страницу входа, проверяет сессии и проксирует DSH.
  Он может сам получать сертификаты Let's Encrypt или работать по HTTP за вашим
  существующим reverse proxy с HTTPS.
- **dsh** содержит Node.js/npm и устанавливает закреплённую версию DSH при первом
  запуске. Процесс работает без root; выделенная папка сервера становится его
  домашним каталогом `/home/dsh`.

Форма входа поддерживает сохранение постоянной пары логин/пароль шлюза
менеджером паролей браузера; его конкретное поведение зависит от браузера.
Меняющийся токен DSH обменивается автоматически внутри системы — искать и копировать
его из логов не нужно. Установка рассчитана на одного владельца рабочего окружения,
без регистрации и разделения данных нескольких пользователей.

## Что потребуется

- Docker Engine с Docker Compose v2 или новее и Python 3.10+ для скрипта настройки.
- Отдельная папка для DSH с правами выбранного непривилегированного UID/GID.
- Домен с HTTPS: либо свободные входящие порты 80/443 для встроенного Let's Encrypt,
  либо уже работающий reverse proxy, который обслуживает HTTPS.
- Исходящий доступ к npm и API выбранной модели. Ключ модели настраивается отдельно
  в DSH; подписка или доступ к API в этот проект не входят.

Интеграционные проверки выполнены с DSH `0.2.1-rc.5` и Node.js `24.22.1` на Linux ARM64
в Docker на OrbStack и Linux AMD64 в GitHub Actions. Результаты и границы проверок —
в [журнале проверки](docs/testing.md).

По умолчанию DSH ограничен 2 CPU, 3 ГиБ памяти и 512 процессами; шлюз — 0,5 CPU
и 128 МиБ памяти. Это начальные лимиты, а не измеренные требования для любой нагрузки.
Подробности хранения и изоляции — в [документации развёртывания](docs/deployment.md).

## Быстрый запуск

Склонируйте репозиторий и создайте локальные настройки:

```sh
git clone https://github.com/ReanSn0w/rdsh.git
cd rdsh
cp .env.example .env
```

В `.env` задайте `PUBLIC_URL`, оставьте проверенную точную версию `DSH_VERSION`
и укажите выделенную папку `DSH_HOME_PATH`. Если запускаете настройку от обычного
пользователя, поставьте `RDSH_UID` и `RDSH_GID` равными результатам `id -u` и `id -g`.
При настройке от root оставьте непривилегированные значения `1000:1000`.
Ноль в этих настройках запрещён. Выберите UID/GID до сборки образов.

Подготовьте домашний каталог и учётные данные:

```sh
python3 scripts/setup.py
```

Скрипт соберёт образ шлюза и запросит пароль без отображения ввода. Закрытые файлы
учётных данных появятся в `secrets/`. Существующие секреты не перезаписываются,
владельцы файлов внутри готового домашнего каталога рекурсивно не меняются.
Логин по умолчанию — `token`; изменить его можно через `AUTH_USERNAME`.

Выберите **один** вариант запуска.

**Встроенный HTTPS.** Укажите `ACME_EMAIL`, направьте домен на сервер и откройте
входящие 80/443:

```sh
docker compose -f docker-compose.yml -f compose.https.yml up -d --build
```

**Существующий reverse proxy на хосте.** Шлюз будет доступен только по
`127.0.0.1:GATEWAY_HTTP_PORT`, по умолчанию — `127.0.0.1:8080`:

```sh
docker compose -f docker-compose.yml -f compose.proxy-host.yml up -d --build
```

Подключите его к прокси по [примеру nginx на хосте](examples/nginx-host.conf).
`PUBLIC_URL` должен содержать внешний **HTTPS**-адрес, хотя между прокси и шлюзом
используется HTTP. В этом режиме ACME выключен, порты 80/443 наш Compose не занимает.

**Существующий reverse proxy в Docker.** Укажите его готовую сеть в `PROXY_NETWORK`:

```sh
docker compose -f docker-compose.yml -f compose.proxy-network.yml up -d --build
```

Направьте домен на `http://rdsh-gateway:8080` по
[примеру nginx в Docker](examples/nginx-docker.conf). Только шлюз подключается
к сети прокси, DSH остаётся в своей сети. Порты на хост в этом варианте не публикуются.

Первый запуск скачивает и устанавливает DSH и может занять несколько минут.
Проверьте состояние:

```sh
docker compose ps
docker compose logs --tail=50 dsh
```

Откройте `PUBLIC_URL`, войдите и настройте модель через предусмотренный в DSH
интерфейс настроек. Не добавляйте ключ API в Dockerfile, образ или публикуемый Compose.
Рабочие проекты создавайте внутри смонтированного домашнего каталога.

## Настройки

| Переменная | Значение по умолчанию / обязательность | Назначение |
| --- | --- | --- |
| `PUBLIC_URL` | обязательный HTTPS URL | Внешний адрес с корневым путём, без префикса вроде `/dsh/` |
| `DSH_VERSION` | точная версия из `.env.example` | Версия установки; `latest` не используется |
| `DSH_HOME_PATH` | `./data/home` | Выделенная папка хоста для `/home/dsh` |
| `RDSH_UID`, `RDSH_GID` | `1000`, `1000` | Владелец данных и процессов; изменение требует пересборки |
| `AUTH_USERNAME` | `token` | Постоянный логин |
| `ACME_EMAIL` | обязателен для встроенного HTTPS | Контакт ACME |
| `GATEWAY_HTTP_PORT` | `8080` | Loopback-порт для reverse proxy на хосте |
| `PROXY_NETWORK` | обязателен для прокси в Docker | Существующая внешняя Docker-сеть |
| `TRUSTED_PROXIES` | пусто | CIDR доверенных прокси, которым разрешено передавать IP клиента |
| `DSH_CPUS`, `DSH_MEMORY` | `2`, `3g` | Ограничения ресурсов DSH |
| `GATEWAY_CPUS`, `GATEWAY_MEMORY` | `0.5`, `128m` | Ограничения ресурсов шлюза |

Хеш пароля и секрет сессий хранятся в отдельных закрытых файлах, а не в `.env`.
Не публикуйте полный вывод `docker compose config` своей изменённой рабочей
конфигурации: добавленные вручную переменные окружения могут содержать секреты.

## Остановка, обновление и смена пароля

В командах используйте тот же override, с которым запускали проект. Например,
для reverse proxy на хосте:

```sh
# Остановить контейнеры, сохранив домашний каталог и именованные тома.
docker compose -f docker-compose.yml -f compose.proxy-host.yml down
# Пересобрать и запустить после обновления кода оболочки.
docker compose -f docker-compose.yml -f compose.proxy-host.yml up -d --build
# Пересоздать только DSH с сохранением домашнего каталога.
docker compose -f docker-compose.yml -f compose.proxy-host.yml up -d --force-recreate dsh
```

Чтобы обновить DSH, сначала обновите оболочку до образа с проверенным lock-манифестом
нужного выпуска, затем задайте эту точную версию в `DSH_VERSION` и пересоздайте DSH.
Произвольная npm-версия без встроенного манифеста не устанавливается. Обычный
перезапуск не скачивает новую версию. Понижение версии программы не отменяет
изменений формата данных, которые мог выполнить upstream.

Чтобы сменить пароль шлюза:

```sh
python3 scripts/setup.py --rotate-password
docker compose -f docker-compose.yml -f compose.proxy-host.yml up -d --force-recreate gateway
```

Пересоздание шлюза отзывает все его сессии. Используйте `--force-recreate`, а не
только `restart`: файл хеша заменяется атомарно, и bind mount нужно подключить
заново. Новый пароль затем можно сохранить в менеджере паролей браузера.

Команда `down -v` удаляет именованные тома — используйте её только намеренно.
Домашний каталог пользователя является bind mount и хранится вне образов.
Резервное копирование и восстановление не входят в rdsh; для них используйте
свои внешние инструменты.

## Частые проблемы

| Симптом | Что проверить |
| --- | --- |
| Скрипт настройки отклоняет права или владельца | Согласуйте UID/GID до сборки; домашнему каталогу нужны права 0700, секретным файлам — 0600. `chmod 777` не требуется. |
| Первая установка завершается ошибкой | Проверьте доступность npm, место на диске и лимит памяти; изучите очищенные от секретов логи DSH. |
| Порты 80/443 заняты | Используйте один из вариантов с внешним прокси вместо встроенного HTTPS. |
| Не выдаётся сертификат | Проверьте DNS A/AAAA, доступность сервера извне и контакт ACME; избегайте многократных попыток production-выдачи подряд. |
| Вход отвечает 401/403 | Проверьте публичный URL, Host/Origin, передаваемые прокси; после перезапуска шлюза войдите заново. |
| Интерфейс открыт, но поток ответов не работает | Проверьте WebSocket upgrade и отключение буферизации в reverse proxy. |
| Шлюз ждёт DSH | Проверьте установку и healthcheck DSH; во время запуска доступ без авторизации не открывается. |

## Границы изоляции

Контейнеры работают без root, privileged-режима, Docker socket и host namespaces.
Их корневые файловые системы доступны только для чтения; данные, временные файлы
и ресурсы выделены явно. DSH может менять всё содержимое своего смонтированного
домашнего каталога, включая настройки и установленные инструменты.

Docker bridge не запрещает исходящие обращения к сервисам хоста, локальной сети
или облачным metadata endpoints. При необходимости такую политику нужно обеспечить
на Docker-хосте и проверить из работающего контейнера. Контейнеры используют общее
ядро; для более сильной границы разворачивайте проект в отдельной виртуальной машине.
Администратор хоста сохраняет доступ к контейнерам и их данным.

## Разработка и проверки

Проверки Compose и скрипта настройки не используют локальные учётные данные:

```sh
python3 -m unittest discover -s tests/integration -p 'test_*.py' -v
```

Полные тесты создают временные проекты Compose с искусственными учётными данными
и реальным DSH, затем удаляют только свои контейнеры и тома. Вызовов платных моделей
в них нет:

```sh
python3 tests/integration/setup-smoke.py
python3 tests/integration/smoke.py --proxy-mode host
python3 tests/integration/smoke.py --proxy-mode network
python3 tests/integration/smoke.py --proxy-mode auto
```

Для этих тестов также нужен `openssl`. Режим `auto` использует временный Pebble ACME
с реальной проверкой домена и проверкой цепочки TLS; production Let's Encrypt
в тестах не используется. Выдача сертификата для конкретного публичного домена
зависит от DNS и доступности сервера владельца.

Протокол выбранного DSH описан в [документе интеграции](docs/dsh-integration.md),
детали компонентов — в [runtime](docs/runtime.md) и [gateway](docs/gateway.md).
[Результаты проверок](docs/testing.md) фиксируют проверенное окружение и ограничения.
[Структура репозитория](docs/repository.md) отделяет исходники от пользовательских
данных. Сборка образа сама по себе не считается проверкой совместимости DSH.
