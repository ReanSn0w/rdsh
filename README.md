# rdsh

Развёртывание [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)
на своём сервере: два контейнера, сохраняемый домашний каталог и привычный вход
по логину и паролю. Это самостоятельная оболочка, а не официальный продукт DeepSeek.

```text
Браузер ── HTTPS ── [внешний reverse proxy, если нужен] ── gateway ── dsh
                                                          │         │
                                                     вход + TLS  /home/dsh
```

- **gateway** обслуживает страницу входа, проверяет сессии и проксирует DSH.
  Он может сам получать сертификаты Let's Encrypt или работать по HTTP за вашим
  существующим reverse proxy с HTTPS.
- **dsh** содержит Node.js/npm и устанавливает закреплённую версию DSH при первом
  запуске. Процесс работает без root; выделенная папка сервера становится его
  домашним каталогом `/home/dsh`.

Форма входа поддерживает сохранение постоянной пары логин/пароль шлюза
менеджером паролей браузера; его конкретное поведение зависит от браузера.
Меняющийся токен DSH обменивается автоматически внутри системы — искать и копировать
его из логов не нужно. Установка рассчитана на одного владельца рабочего окружения,
без регистрации и разделения данных нескольких пользователей.

## Быстрый запуск

Понадобятся Docker Engine с Compose v2, Bash, `curl`, `tar` и домен, направленный
на сервер. Порты **80 и 443** должны быть свободны и доступны извне. Python и Git
для установки не нужны.

Скачайте установщик из `master`, выполните его и удалите временный скрипт:

```sh
(
  rdsh_installer=$(mktemp) || exit 1
  trap 'rm -f "$rdsh_installer"' EXIT
  curl --fail --silent --show-error --location --proto '=https' --proto-redir '=https' \
    https://raw.githubusercontent.com/ReanSn0w/rdsh/master/scripts/install.sh \
    --output "$rdsh_installer" &&
  bash "$rdsh_installer" ./rdsh
) && cd rdsh
```

Будет создана **новая** папка `rdsh` с `docker-compose.yml`, `.env`, исходниками
двух образов (`gateway/`, `dsh/`) и `data/home/`. Установщик скачивает один архив
`master`, подбирает UID/GID и выставляет права; контейнеры пока не запускает.
Существующую папку он не перезаписывает. Вместо `./rdsh` можно указать другой новый
каталог внутри существующей папки.

Откройте `.env` и заполните:

- `PUBLIC_URL` — адрес вида `https://dsh.example.com`, без префикса пути.
- `ACME_EMAIL` — контакт для Let's Encrypt.
- `AUTH_PASSWORD_HASH` — хеш пароля, полученный следующей командой:

```sh
docker compose run --build --rm --no-deps gateway hash-password
```

Команда работает **до первого запуска** и до заполнения `.env`. Она собирает только
шлюз, запрашивает пароль дважды без отображения ввода и выводит bcrypt-хеш. Пароль
должен занимать 12–72 байта UTF-8. DSH и публичные порты при этом не запускаются.

Вставьте хеш в `.env` **в одинарных кавычках**, сохранив все символы `$`:

```dotenv
AUTH_PASSWORD_HASH='$2a$12$...полный хеш из команды...'
```

Одинарные кавычки исключают интерполяцию `$` внутри значения
([правила Docker Compose](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/#env-file-syntax)).
Исходный пароль в `.env` не записывается. Хеш доступен администратору Docker через
окружение контейнера; не публикуйте `.env` и полный вывод `docker compose config`.

Запустите:

```sh
docker compose up -d
```

Compose соберёт недостающие образы, DSH установится в HOME, а шлюз автоматически
получит и будет продлевать сертификат Let's Encrypt. Первый запуск занимает несколько
минут. Встроенный ACME-клиент принимает условия Let's Encrypt при регистрации.

```sh
docker compose ps
docker compose logs --tail=50 dsh
```

Откройте `PUBLIC_URL`. Логин по умолчанию — **`token`**, пароль — тот, из которого
вы получили хеш. Затем настройте API-ключ модели в DSH. Подписка и стоимость API
в проект не входят. Рабочие проекты создавайте внутри `/home/dsh`.

## Настройки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PUBLIC_URL` | заполнить | Внешний HTTPS origin без префикса `/dsh/` |
| `ACME_EMAIL` | заполнить | Контакт Let's Encrypt |
| `AUTH_USERNAME` | `token` | Постоянный логин |
| `AUTH_PASSWORD_HASH` | заполнить | bcrypt-хеш в одинарных кавычках |
| `DSH_VERSION` | `0.2.1-rc.5` | Точная версия с встроенным проверенным lock-манифестом |
| `DSH_HOME_PATH` | `./data/home` | Выделенная папка хоста, смонтированная как `/home/dsh` |
| `RDSH_UID`, `RDSH_GID` | определяет установщик | Владелец HOME и контейнерных процессов |
| `DSH_CPUS`, `DSH_MEMORY` | `2`, `3g` | Лимиты ресурсов DSH |
| `GATEWAY_CPUS`, `GATEWAY_MEMORY` | `0.5`, `128m` | Лимиты ресурсов шлюза |

При запуске установщика обычным пользователем берутся его UID/GID; от root —
`1000:1000`. Менять эти значения после подготовки HOME без перенастройки владельцев
и пересборки образов нельзя. Для другого `DSH_HOME_PATH` заранее создайте выделенную
папку с этими владельцами и правами `0700`. Не монтируйте свой настоящий домашний каталог.

Ключ подписи сессий шлюз создаёт сам в памяти при каждом запуске. Отдельный файл
секрета не нужен; перезапуск шлюза завершает все его сессии.

## Управление

```sh
# Остановить, сохранив HOME и именованные тома.
docker compose down
# Запустить снова.
docker compose up -d
# Пересобрать после обновления исходников образов.
docker compose up -d --build
```

Для смены пароля получите новый хеш в работающем шлюзе:

```sh
docker compose exec gateway /usr/local/bin/rdsh-gateway hash-password
```

Обновите `AUTH_PASSWORD_HASH` в `.env`, затем примените новое окружение:

```sh
docker compose up -d --force-recreate gateway
```

`restart` не перечитывает `.env`. Если шлюз остановлен, используйте команду
`docker compose run --build --rm --no-deps gateway hash-password` из быстрого старта.
Генерация хеша сама по себе не меняет пароль.

Установщик предназначен для новой установки, а не для обновления поверх данных.
При обновлении оболочки перенесите новые исходники `gateway/`, `dsh/` и нужные изменения
Compose, сохранив свою `.env` и `data/`, затем пересоберите образы. Для обновления DSH
нужен выпуск оболочки с lock-манифестом нужной версии: измените `DSH_VERSION` и
пересоздайте DSH. Обычный перезапуск новую версию не скачивает.

`down -v` удаляет именованные тома, включая состояние ACME; используйте намеренно.
HOME хранится отдельно на хосте. Резервное копирование и восстановление — вне проекта.

## Если уже есть reverse proxy

Основной Compose рассчитан на собственный HTTPS. Для внешнего прокси измените его:
выставьте шлюзу `TLS_MODE: external`, уберите публикацию 80/443 и подключите прокси
к HTTP-порту шлюза `8080`. `PUBLIC_URL` остаётся **внешним HTTPS-адресом**.
Порт DSH публиковать не нужно.

Прокси должен передавать исходный Host и WebSocket upgrade и поддерживать потоковые
ответы. Способ соединения и сертификаты настраиваются в вашем прокси. Детали,
примеры nginx и необязательные Compose overrides — в [документации](docs/deployment.md).

## Частые проблемы

| Симптом | Что проверить |
| --- | --- |
| Установщик отклоняет каталог | Он создаёт только новую папку и не перезаписывает существующие данные. |
| DSH не может писать в HOME | Владелец должен совпадать с UID/GID образа, права папки — `0700`. |
| Первая установка не завершается | Доступ к npm, место на диске, лимит памяти и логи DSH. |
| Порты 80/443 заняты | Освободите их для rdsh либо настройте внешний прокси. |
| Не выдаётся сертификат | DNS A/AAAA и доступность обоих портов извне. |
| Шлюз отклоняет хеш | Полный bcrypt-хеш в одинарных кавычках, без потерянных `$`. |
| Вход отвечает 401/403 | Правильный PUBLIC_URL и Host/Origin; после перезапуска войдите снова. |

## Границы изоляции

Контейнеры работают без root, privileged-режима, Docker socket и host namespaces.
Их корневые файловые системы доступны только для чтения; данные, временные файлы
и ресурсы выделены явно. DSH может менять всё содержимое своего смонтированного
домашнего каталога, включая настройки и установленные инструменты.

Docker bridge не запрещает исходящие обращения к сервисам хоста, локальной сети
или облачным metadata endpoints. При необходимости такую политику нужно обеспечить
на Docker-хосте и проверить из работающего контейнера. Контейнеры используют общее
ядро; для более сильной границы разворачивайте проект в отдельной виртуальной машине.
Администратор хоста сохраняет доступ к контейнерам и их данным.

## Разработка и проверки

Проверки Compose и Bash-установщика не используют локальные учётные данные:

```sh
python3 -m unittest discover -s tests/integration -p 'test_*.py' -v
```

Полные тесты создают временные проекты Compose с искусственными учётными данными
и реальным DSH, затем удаляют только свои контейнеры и тома. Вызовов платных моделей
в них нет:

```sh
python3 tests/integration/setup-smoke.py
python3 tests/integration/smoke.py --proxy-mode host
python3 tests/integration/smoke.py --proxy-mode network
python3 tests/integration/smoke.py --proxy-mode auto
```

Для этих тестов также нужен `openssl`. Режим `auto` использует временный Pebble ACME
с реальной проверкой домена и проверкой цепочки TLS; production Let's Encrypt
в тестах не используется. Выдача сертификата для конкретного публичного домена
зависит от DNS и доступности сервера владельца.

Протокол выбранного DSH описан в [документе интеграции](docs/dsh-integration.md),
детали компонентов — в [runtime](docs/runtime.md) и [gateway](docs/gateway.md).
[Результаты проверок](docs/testing.md) фиксируют проверенное окружение и ограничения.
[Структура репозитория](docs/repository.md) отделяет исходники от пользовательских
данных. Сборка образа сама по себе не считается проверкой совместимости DSH.
